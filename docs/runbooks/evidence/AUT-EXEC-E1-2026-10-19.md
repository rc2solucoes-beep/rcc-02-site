### 3.1 Sobre `--bail 1` (verificado por inspeção, não por execução)

- `vitest run --help` (Vitest 4.1.5) documenta `--bail <number>`: interrompe a execução quando esse número de testes falha (padrão 0). `npm run … -- --bail 1` repassa o argumento ao `vitest run --config vitest.integration.config.ts`. A configuração **não** define `bail`; não foi alterada.
- Em `vitest/dist/chunks/index.*.js`, `onAfterRunTask` chama `testRunner.cancel("test-failure")` quando as falhas atingem o limite. Em `@vitest/runner`, `runSuite` executa o `afterAll` num bloco `finally` ("afterAll runs even if beforeAll or suite children fail"). Logo, **pela leitura do código**, o `afterAll` de limpeza de cada arquivo roda mesmo com o cancelamento.
- **Ressalvas.** (a) Com o cancelamento, os testes pendentes são marcados como ignorados e o teste em curso recebe um sinal de aborto; uma requisição em voo pode ser interrompida. (b) Os arquivos seguintes **não** rodam: o relatório da matriz fica parcial. (c) O `afterAll` só protege o processo vivo: com `Ctrl+C` ou queda, o registro em memória se perde (lacuna 1 do CC-7). (d) Que o `afterAll` realmente conclui a limpeza sob `--bail` **só se comprova na execução e na consulta de resíduos**; a ausência de falhas nos testes locais não comprova isso.
- Alternativa se o responsável preferir não usar `--bail`: remover `-- --bail 1`. A decisão do responsável de 19/10/2026 foi "usar, quando compatível".
